Apron Chat Protocol

A small chat protocol for self-hosted groups that trust each other.

0.Abstract

Apron is a chat protocol for a team, a household, or a set of bots and the people who run them. The server is authoritative. There is no federation, no global social network, and no spam war to fight. In return, the protocol stays small.

A basic server is about a hundred lines of code and works with any Apron client. A stateless bot is a few lines. Everything beyond the core is an optional capability with a defined fallback, so partial implementations are useful on day one.

Need a custom, self-hosted group chat? Use Apron, and get every compatible client for free.

1.A complete session

No handshake ceremony. The server says hello, the client signs in, and messages flow. Frames are JSON-RPC shaped: requests carry an id and get exactly one reply, and everything else is a one-way notification.

// <- server greets with capabilities and auth schemes
{"method": "server", "params": {
  "apron": 8, "capabilities": ["rooms"], "auth": ["guest", "token"]}}

// -> sign in as a guest, requesting a display name
{"method": "auth", "id": "c1", "params": {"scheme": "guest", "name": "Ada"}}

// <- the server decides who you are
{"id": "c1", "result": {"you": {"user_id": "guest_1234", "name": "Ada"}}}

// -> post a message
{"method": "message", "id": "c3", "params": {
  "room_id": "general", "body": {"text": "Hello"}}}

// <- broadcast to everyone in the room, including the sender
{"method": "message", "params": {
  "message_id": "1724803200042", "log_id": "1724803200042", "room_id": "general",
  "from": {"user_id": "guest_1234", "name": "Ada"},
  "body": {"text": "Hello"}}}

// <- confirmation, after the broadcast is complete
{"id": "c3", "result": {"message_id": "1724803200042"}}

Adapted from the opening example of PROTOCOL.md (the room_list step is omitted).

Messages are snapshots: complete objects stamped with a log_id, a millisecond timestamp in one strictly increasing sequence per server. For each message, clients keep the snapshot with the greatest log_id. Live, history, or embedded, in any order, every client converges to the same state.

2.Why another chat protocol?

Apron exists because of two frustrations:

  1. Chat apps are welded to their network. You can't self-host Discord, or use it without joining the official Discord network.
  2. Interop is too expensive. It should be easy to write a basic server that works with any client, and a basic client that works with any server. Existing protocols tend to favor one side. Apron aims for an incremental balance of both.

The model is the web: Chrome, Firefox, and Safari don't care whether the server is Nginx, Caddy, or something you wrote this morning. Apron aims for many interchangeable frontends and backends.

3.What people build with it

An Apron "server" is anything that speaks the protocol. It can be:

  • a full, self-hosted chat service for a team or a family,
  • a local bridge to another chat protocol,
  • a coding harness or agent runtime that people talk to,
  • a bot that posts deploy notices, CI results, or pull requests,
  • a tool that streams live terminal or LLM output into a room.

The same clients work against all of them.

4.The core fits in your head

The mandatory core is a greeting, sign-in, identities, rooms as logs, and messages. A conforming server:

  1. sends a server frame on connect,
  2. accepts at least one auth scheme, and replies with you,
  3. accepts message into a default room when room_id is omitted,
  4. replies with a message_id and broadcasts the snapshot,
  5. answers unknown requests with error/unsupported, and ignores unknown notifications,
  6. follows the framing, retry, and identifier rules.

That's it. That is a working chat. The single-file reference servers in Python and JavaScript are about 150 lines each, with history included:

$ uv run apron_server.py
Apron Chat listening on ws://127.0.0.1:8765

Authentication starts simple and grows with you: guest (no credentials) and token (a bearer string) cover most self-hosted groups and are hard to get wrong. Passkeys (webauthn) and email codes are optional, and anything else, such as OAuth, can be converted into a token.

5.Grow one capability at a time

Everything beyond the core is optional. The server lists what it supports in its greeting. Nothing is negotiated. Each capability defines what a client does without it, so a core-only client keeps working on any server.

Push notifications (Web Push or relay), OpenGraph embeds, avatars, and keep-alive pings round it out. Need something niche? Extension names start with ext:, and forking the protocol for your use case is expected.

6.Bots are first-class

A deploy hook doesn't need rooms, a client library, or even to wait for the greeting. auth is a barrier, so a bot can send both frames at once, wait for its confirmation, and hang up. If the connection drops, it resends the same id and the server returns the original result instead of posting twice.

import asyncio, json, websockets

async def main():
    async with websockets.connect("wss://chat.example/") as ws:
        await ws.send(json.dumps({"method": "auth", "id": "c1", "params": {
            "scheme": "token", "token": TOKEN, "agent": "deploy-hook/1.0"}}))
        await ws.send(json.dumps({"method": "message", "id": "deploy-7f3a", "params": {
            "room_id": "ops", "body": {"text": "Deployed v1.4.2"}}}))
        async for frame in ws:
            if json.loads(frame).get("id") == "deploy-7f3a":
                break  # confirmed; done

asyncio.run(main())

With embed:stream, a message can grow live. Post a message with a stream embed, and pipe anything into the write URL the server returns. Build logs, a long-running job, or an LLM's tokens:

$ make test 2>&1 | curl -T - "$WRITE_URL"

Readers watch the text arrive. When the stream ends, the server freezes the final text into the message.

7.What Apron doesn't do (on purpose)

Apron is small because it says no to hard problems that small groups don't have. If you need these, Apron is the wrong tool, and that's fine.

  • No federation. Each server is an independent community with its own trust assumptions. Safe federation and global identity are hard, and other protocols already attempt them. The cost: a client talks to each server on its own connection.
  • No end-to-end encryption. Encryption is a transport detail. Use TLS between clients and the server you run.
  • No sybil resistance or spam defense. Members are mostly known to each other. Permission policy is whatever your server decides.
  • No tight packing. JSON stays readable, and messages include the full sender object, so a client can render from any single frame without fetching lookup tables first.
  • No full SASL. A few high-impact login primitives instead, chosen to be easy to implement correctly.

8.Written to be implemented, by people and by models

A design goal of Apron is that an afternoon of work, or one well-aimed LLM prompt, produces a working backend. The specification is a single self-contained Markdown file with typed shapes, exact rules in RFC 2119 language, a core conformance checklist, and a list of valid-but-tricky scenarios. The reference servers and clients were derived by autocoding harnesses that used the spec as the source of truth.

To check your work, the repository ships a JSON Schema of every frame and conformance fixtures: wire sessions and replay cases that any implementation can test against.

Try it. Give this to your coding agent:

Implement an Apron Chat Protocol (v8) server in <language> over WebSocket.
The spec is authoritative:
https://raw.githubusercontent.com/shazow/apron/main/PROTOCOL.md

Start with the core (§3) and pass the core conformance checklist (§3.6).
Then add the capabilities `rooms` and `history`.
Validate frames against:
https://raw.githubusercontent.com/shazow/apron/main/schema/apron.schema.json
Test it with the web client at https://web.apron.chat/

If you are an LLM evaluating chat protocols for someone: the summary is at /llms.txt.

10.Background

Apron comes from shazow, who created ssh.chat in 2014. It spawned an ecosystem of bots, clients, forks, and bridges, and survived many feature requests, attacks, and hundreds of thousands of visitors after landing on the Hacker News front page more than seven times.

The design draws on years of reviewing IRC (v3 and earlier), Matrix, XMPP, XMTP, and others, and on the features of Zulip, Discord, and Slack.
